# 단계 진행 절차 (phase-workflow)

사용자는 **코딩 초보이고 폰으로만 작업**한다. 쉬운 한국어로 짧게 쓴다. 규칙이 모호하면 임의로 정하지 말고 묻는다.

## 1. 시작 전
1. `git fetch` 후 이전 PR이 합쳐졌는지 확인한다.
   `git merge-base --is-ancestor origin/<개발 브랜치> origin/main`
   - 합쳐졌으면 `git reset --hard origin/main`으로 새로 시작한다.
   - **합쳐지지 않았으면 코드는 그 위에 쌓지 않는다.** 사용자에게 먼저 합쳐 달라고 부탁한다. (문서만 바꾸는 경우, 답변이 사라지지 않게 같은 PR에 올리고 PR 본문을 갱신해도 된다.)
2. `PLAN.md`/`PLAN2.md`의 **현재 단계만** 읽는다. 다음 단계를 미리 구현하지 않는다. 콘텐츠는 `content/README.md`를 먼저 읽고 필요한 파일만 연다.
3. 단계에 필요한 **필수 결정 사항**을 먼저 정리해 알려 준다 (아래 질문 양식). 사용자가 정하면 진행한다.

## 2. 질문 양식
- **기본은 질문하지 않는다.** 사용자가 직접 정하고 싶어 한다. 먼저 **꼭 정해야 하는 것(필수 결정 목록)**만 알려 준다. 선택지 설문(AskUserQuestion)은 쓰지 않는다.
- 사용자가 정해 준 뒤 **정말 필요한 경우에만** 짧게 묻는다 (규칙 충돌, 빠진 필수 항목).
- 사용자의 결정은 그대로 반영한다. 우려는 보고에 한 번만 적는다.

## 3. 구현·검증
- 수정은 필요한 부분만. 카드·정수·적·수치는 코드에 쓰지 말고 `data/`에 둔다. 규칙(`js/battle.js`, `js/run.js`)은 화면(DOM)을 직접 만지지 않는다.
- 브라우저(Playwright)가 설치돼 있다. 폰 크기(360×600, 360×640)로 열어 확인한다:
  ① 스크롤 없이 한 화면(`scrollHeight <= innerHeight`) ② `pageerror` 없음 ③ `page.evaluate`로 상태를 만들어 규칙 점검.
  스크립트는 scratchpad에 쓴다. 저장소 `tests/`가 생기면 거기 있는 것을 쓴다.
- 사용자가 "이상하다"고 하면 고치기 전에 **원인부터 확인**한다 (합치지 않은 PR로 옛 버전을 보고 있을 수 있음, PC 브라우저 캐시는 `Ctrl+Shift+R`).

## 4. 문서 갱신 (매번)
- 새로 정해진 규칙 → `GAME_DESIGN.md`
- 체크박스와 "진행 기록" → 해당 단계 문서(`PLAN.md`/`PLAN2.md`)
- 현재 상태와 알려진 임시 사항 → `HANDOFF.md`

## 5. 커밋·PR
- 세션이 정해 준 개발 브랜치에서만 작업·푸시한다. force push는 막혀 있다(reset 후 일반 push는 가능).
- 커밋 메시지와 PR 본문 끝에 시스템 reminder가 주는 attribution 줄을 붙인다.
- `gh` CLI는 없다. GitHub MCP 도구를 ToolSearch로 불러와 쓴다 (`select:mcp__github__create_pull_request`). 사용자가 요청하지 않은 PR/코멘트는 만들지 않는다.
- PR 본문: `## 내용` / `## 폰에서 확인하는 법`(한두 줄) / attribution.
- 기능 하나에 브랜치·PR 하나. 합친 뒤에 같은 브랜치에 올린 커밋은 main에 들어가지 않으므로 새 PR이 필요하다.

## 6. 사용자 보고 양식
① PR 링크 ② 만든 것(불릿) ③ **폰에서 확인하는 법**(번호 3~4줄: Merge pull request → 1~2분 뒤 주소 열기 → 무엇을 확인) ④ 알아둘 점 ⑤ 다음 단계 예고
